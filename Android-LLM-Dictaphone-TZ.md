# Техническое задание  
## Android‑приложение «LLM Веб‑диктофон»

---

## 1. Цель проекта

Создать нативное Android‑приложение, которое позволяет пользователю:

1. Записывать голос с микрофона устройства.
2. Надёжно сохранять аудиозапись локально на телефоне (даже для часовых встреч).
3. По желанию:
   - получать онлайн‑транскрипцию по мере речи (квази‑реалтайм / стриминг),
   - либо записывать встречу полностью офлайн и отправить её на сервер **после завершения**, когда есть сеть.
4. Отправлять аудио на сервер (чанками или целиком) для распознавания и LLM‑обработки.
5. Получать расшифровку и отображать её:
   - в режиме «ленты» (текст течёт вниз, как чат),
   - или как итоговый текст после полной обработки.
6. После завершения записи запускать сценарии обработки («Просто текст», «Резюме встречи», другие режимы) и получать структурированный результат.
7. Работать с историей записей (просмотр, переименование, удаление, повторная обработка).
8. Работать в рамках учётной записи пользователя (авторизация, привязка записей к пользователю, удаление аккаунта со всеми данными).

---

## 2. Область действия и платформы

- **Платформа:** Android 10+ (API level 29 и выше).
- **Устройства:** смартфоны, основная ориентация — портретная.
- **Сетевые требования:**
  - Все запросы к backend — по HTTPS.
  - Возможность работы как по Wi‑Fi, так и по мобильной сети.
- **Backend:**
  - Используется существующий backend (аналог текущего Node/Express сервера: `/api/recordings`, `/api/prompts`, `/api/auth`, `/api/admin/users`, Realtime‑WS‑мост).
  - Приложение не должно жёстко зависеть от конкретной реализации — API должно быть инкапсулировано в модуле «data / repository».

---

## 3. Основные сценарии использования

### 3.1. Запись и онлайн‑отображение текста (онлайн‑режим)

1. Пользователь авторизован и находится на главном экране.
2. Видит:
   - кнопку «Начать запись»,
   - пустую (или заполненную) ленту текста,
   - строку статуса: «Готов к записи».
3. Пользователь нажимает «Начать запись».
4. Приложение запрашивает доступ к микрофону:
   - при отказе показывает понятное сообщение и инструкцию (как включить доступ в настройках Android).
5. Приложение стартует запись:
   - аудио захватывается через `AudioRecord` или `MediaRecorder` (моно, PCM16, 16–24 kHz),
   - данные параллельно:
     - **пишутся в локальный файл** (внутреннее хранилище приложения),
     - и/или буферизуются для отправки на сервер (см. 5.2).
6. Если выбран онлайн‑режим:
   - каждые N миллисекунд/секунд (например, 3–5 сек) формируется чанк,
   - чанк отправляется на сервер (HTTP или WS),
   - сервер возвращает текст фрагмента или обновлённую транскрипцию,
   - приложение добавляет новые элементы в ленту (как сообщения в чате),
   - лента автоматически скроллится к последнему элементу.
7. Пользователь нажимает «Остановить запись»:
   - запись микрофона немедленно прекращается,
   - при необходимости отправляется последний чанк или сигнал завершения,
   - статус меняется на «Запись завершена».

### 3.2. Запись с локальным накоплением и последующей обработкой (офлайн/отложенный режим)

1. Пользователь выбирает режим «Записать и обработать позже» или приложение автоматически переключается в этот режим при отсутствии сети.
2. При нажатии «Начать запись»:
   - аудио записывается **в локальный файл** (например, `m4a`/`webm`) **по мере записи**, без накопления в памяти;
   - онлайн‑отправка чанков не выполняется, либо выполняется только при наличии сети и небольших фрагментах.
3. По окончании записи:
   - запись закрывается, локальный файл фиксируется (есть метаданные о длительности/размере).
4. Далее возможны варианты:
   - при наличии сети — приложение предлагает «Отправить на сервер и расшифровать»,
   - при отсутствии сети — запись остаётся со статусом «ожидает обработки», пользователь позже (из истории) запускает «Отправить и расшифровать».
5. При запуске обработки:
   - локальный файл отправляется на backend **частями** (чанками) или целиком, в зависимости от серверных ограничений;
   - сервер выполняет транскрибацию и сохраняет транскрипт;
   - клиент получает результат и отображает.

### 3.3. Выбор и запуск обработки текста

1. После завершения записи (онлайн или офлайн) пользователю доступен блок обработки:
   - режимы: «Просто текст», «Резюме встречи», другие сценарии (из `prompts`).
2. Пользователь выбирает режим и нажимает «Обработать».
3. Клиент отправляет запрос на `/api/recordings/:id/process` с `recordingId` и `mode`.
4. Backend получает полную транскрипцию, отправляет её в LLM и сохраняет результат.
5. Клиент отображает результат в отдельном блоке:
   - исходный текст (нередактируемый),
   - результат обработки (может отличаться по структуре в зависимости от режима),
   - кнопка «Копировать результат».

### 3.4. История записей и локальное хранение

1. Экран «История» показывает список записей:
   - локальные записи с привязкой к серверным `recordingId` (если они уже отправлены),
   - статус: «записана локально», «отправлена», «расшифрована», «ошибка».
2. Для каждой записи пользователь может:
   - открыть локальную транскрипцию / отправить на сервер, если ещё не расшифровано,
   - повторно запустить LLM‑обработку (например, с другим режимом),
   - переименовать запись (локальный title + синхронизация на backend),
   - удалить запись:
     - локально (удалить файл и запись из локальной БД),
     - и/или с сервера (по запросу `DELETE /api/recordings/:id`), если запись уже выгружена.
3. Должна быть возможность получить доступ к записи, которая уже есть на сервере, даже если локальный файл был удалён (т.к. audio может храниться на backend).

### 3.5. Пользователь и управление аккаунтом

1. Экран входа:
   - email + пароль, запрос к `/api/auth/login`.
2. Экран регистрации:
   - email, имя, пароль, `/api/auth/register`,
   - статус `pending`, пока админ не активирует пользователя.
3. Экран «Аккаунт»:
   - отображает e‑mail, роль, статус,
   - позволяет выйти,
   - позволяет удалить аккаунт и все связные данные на сервере (`DELETE /api/me`).
4. При удалении аккаунта:
   - локальные записи и транскрипты также удаляются с телефона для этого пользователя.

## 4. Требования к пользовательскому интерфейсу (UI/UX)

- **Главный экран:**
  - Крупная кнопка записи (FAB или большая кнопка в нижней части экрана).
  - Лента текста (RecyclerView/Compose LazyColumn) с отдельными блоками фрагментов.
  - Строка статуса в верхней части.
  - Индикатор режима: онлайн/офлайн.
- **Экран обработки:**
  - Выпадающий список/меню режимов обработки (plain, meeting_summary, другие).
  - Кнопка «Обработать».
  - Отдельные блоки:
    - «Оригинальная транскрипция» (read‑only),
    - «Результат обработки» + кнопка «Копировать».
- **Экран истории:**
  - Список карточек: название, дата/время, статус, длительность.
  - Действия по свайпу или в overflow‑меню: «Открыть», «Обработать», «Отправить на сервер», «Скачать аудио», «Переименовать», «Удалить».
- **Экран аккаунта:**
  - Краткая информация о пользователе.
  - Кнопки «Выйти», «Удалить аккаунт».
- Адаптивность:
  - Поддержка разных плотностей экранов (использовать `dp`/`sp`),
  - Корректная работа в портретном и ландшафтном режиме (минимум — не ломаться).

## 5. Функциональные требования к Android‑клиенту

### 5.1. Аудиозапись и локальное хранение

- Использовать:
  - либо `AudioRecord` с буферизацией PCM16 и самостоятельной записью в файл,
  - либо `MediaRecorder` с выводом в `File` (например, MPEG‑4 / AAC).
- Файл должен записываться **потоково** (append в файл), без накопления полного аудио в оперативной памяти.
- Минимизировать использование большого буфера в памяти:
  - размер аудиобуфера в несколько секунд, не больше.

### 5.2. Отправка аудио на сервер

Поддерживаются два сценария:

1. **Онлайн‑чанки (квази‑реалтайм):**
   - Параллельно с записью в файл небольшой буфер отправляется на сервер каждые N секунд.
   - Для каждого чанка:
     - вызов `/api/recordings/:id/chunks` с бинарным файлом или base64,
     - получение частичной транскрипции и обновление UI.
   - Аудио целиком при этом всё равно хранится локально.

2. **Отложенная отправка (офлайн):**
   - В период отсутствия сети приложение **только пишет файл локально**.
   - При восстановлении сети пользователь вручную или автоматически инициирует отправку:
     - файл разбивается на части приемлемого размера (например, по 10–20 МБ),
     - части отправляются последовательно на сервер (либо как отдельные записи, либо серверам доверяется сборка на своей стороне).

Требования:

- Размер одного HTTP‑запроса должен быть ограничен (например, не более 25–50 MB) для учёта серверных лимитов.
- Переподключение и повторные попытки при временных сетевых ошибках.
- Информирование пользователя о статусе отправки/обработки (progress‑бар, статусы «Отправляю…», «Ожидает сети», «Готово», «Ошибка»).

### 5.3. Локальное хранилище записей и метаданных

- Использовать Room (SQLite):
  - Таблица `recordings_local`:
    - `localId` (primary key),
    - `serverId` (nullable, когда запись уже есть на backend),
    - `title`,
    - `createdAt`, `updatedAt`,
    - `durationMs`,
    - `filePath` (путь к локальному аудиофайлу),
    - `status` (`local_only`, `uploading`, `uploaded`, `transcribed`, `error`),
    - `transcriptPreview` (первые N символов, для быстрого отображения).
  - Таблица `processing_results` (по желанию на клиенте, можно кэшировать ответы LLM).
- Для экономии места:
  - возможность ограничивать максимальный общий размер кэша,
  - настройки очистки: удалять старые локальные файлы, если есть копия на сервере.

### 5.4. Авторизация и сессия

- Использовать backend‑маршруты:
  - `POST /api/auth/login / register / logout`,
  - `GET /api/auth/me`.
- Хранить сессионные куки/токены в `OkHttp` cookie‑jar или эквиваленте.
- При старте приложения:
  - проверять `auth/me`,
  - при 401 показывать экран входа.

### 5.5. Работа с сетью и жизненным циклом

- Обрабатывать:
  - смену сети (Wi‑Fi ↔ мобильная),
  - временное отсутствие сети (отложенная отправка).
- Долгие записи:
  - использовать ForegroundService с уведомлением «Идёт запись…»,
  - при закрытии приложения запись должна быть либо корректно остановлена, либо продолжена в сервисе (конкретное решение — согласовать).

## 6. Взаимодействие с backend

- Перечень основных эндпоинтов:
  - `/api/recordings` (GET) — список записей (по пользователю),
  - `/api/recordings/:id/chunks` (POST) — загрузка аудио (чанк или целый файл),
  - `/api/recordings/:id/finish` (POST) — явное завершение записи,
  - `/api/recordings/:id` (GET/PATCH/DELETE) — информация/переименование/удаление,
  - `/api/recordings/:id/transcript.txt` (GET) — скачать транскрипт,
  - `/api/recordings/:id/audio` (GET) — скачать аудио,
  - `/api/recordings/:id/process` (POST) — обработка текста LLM,
  - `/api/prompts` (GET/PUT) — конфигурация промптов (для админа),
  - `/api/auth/*`, `/api/me`, `/api/admin/users/*` — аутентификация и админ‑функции.
- Для realtime‑режима:
  - WebSocket‑подключение к backend‑мосту (аналог `/realtime-ws-proxy`),
  - формат сообщений — как в актуальной серверной реализации (тип сообщения, base64 PCM16, события `transcript.text.delta` и т.д.).

---

## 7. Хранение и управление данными

- **На сервере:** использовать текущую модель (Запись, Чанк, Результат обработки) с привязкой к пользователю и политикой хранения (30/90 дней и т.п.).
- **Локально на устройстве:**
  - аудиофайлы в приватном хранилище приложения (без доступа других приложений),
  - метаданные и кэш транскрипций — в Room.
- Возможность:
  - удалить всё локальное содержимое для конкретного пользователя при выходе/удалении аккаунта,
  - при повторной авторизации — восстановить историю с сервера (без локальных аудиофайлов, если они были удалены).

## 8. Нефункциональные требования

- **Производительность:**
  - Задержка онлайн‑режима: 1–3 секунды между фрагментом речи и появлением текста.
  - Офлайн‑режим: допускается задержка на отправку/обработку после встречи (в пределах нескольких секунд/десятков секунд).
- **Надёжность:**
  - Отсутствие потери аудио даже при:
    - падении приложения,
    - временной потере сети,
    - полном отсутствии сети во время записи.
  - Минимизация риска переполнения памяти — запись сразу в файл, а не в оперативную память.
- **Безопасность:**
  - только HTTPS,
  - минимум разрешений (микрофон, foreground‑сервис),
  - корректная работа с персональными данными (голос, текст).
- **Энергопотребление:**
  - использование wake lock/foreground service только во время активной записи.

## 9. Возможные направления развития

- Поддержка:
  - пометки спикеров (speaker diarization),
  - выделения задач/решений отдельными режимами LLM‑обработки,
  - интеграции с календарём Android (привязка записи к событию).
- Продвинутый офлайн‑режим:
  - локальная транскрибация (on‑device ASR) при отсутствии сети,
  - последующая сверка/улучшение транскрипта через сервер при появлении соединения.
